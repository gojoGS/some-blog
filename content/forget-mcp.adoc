MCP is a glorified stateful JSON-RPC spec. MCP v2026-07-28 (aka 2.0) is a glorified stateless JSON-RPC. You're now a 10x senior AI specialist, congrats.

I may be too harsh with the protocol. Discoverability by agents sounds nice. My gripe with MCP comes from the fact
that it's nothing new.
The main argument for using it is popularity. Most company trying to ride the AI train release an MCP server and calls it a day.
It exposes service resources and tools in a way that makes consuming them with any non-agent tool awkward.

Guess what, there already is a way to transport a representation of some server resource. It has stellar support on any software 
platform. The bare install of some Windows editions and Linux distros bundle a client for using it. Even your browser can 
use it.

Yeah, it's REST.

== You don't know the REST...

When you look at https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm[the soul of Roy Fielding's description of REST],
it's fucking awesome. I mean, there are inventions and there are discoveries. REST is the latter.
It feels like a natural product of how things work on the web. Its idea is simple.
When described, it feels like how humans navigate and discover systems.
And that's nothing like how I'd describe the web APIs I've worked on.

Even as someone who had the source code and [.line-through]#the documentation# a stale Confluence document with some details,
I wouldn't be the consumer of the APIs the companies I worked at developed. I don't want to be the GNU/Linux guy,
but they were *RESTish* HTTP APIs with some JSON. They had some parts of REST, minus the good stuff.
No HATEOAS. No proper caching. Everything is a 400 (I was glad when that project ended). Each resource has at most one endpoint, end of story.

This is not the type of architecture you write home about.

For me, what encapsulates REST is that if you sat down with a comfy HTTP client and the base URL of the API, you can
explore it. `GET https://api.example.com/` is the `man man` or `command --help` of the web.

== The REST is [.line-through]#history# the future.

We have a dynamic client in our hands. *Use it.*

I want every major service's API to work like this:

[source,http]
----
GET https://train.org
Accept: application/json
----

[source,json]
----
{
  "_links": {
    "docs": {
      "href": "/docs"
    },
    "trains": { "href": "/trains"},
    "stations": { "href": "/stations"},
    "tickets": {
      "href": "/tickets",
      "docs": {
        "href": "/docs/payment"
      }
    }
  }
}
----

This style represents not only the state, but the *allowed state transitions* of a resource: 

.An instance of the invitation resource in pending state
[source,jsonc]
----
// GET /invitation/15623
{
  "status": "PENDING",
  "_links": {
    "action-remind": {
      "href": "/invitations/15623/reminders",
      "docs": {
        "href": "/docs/invitations/action-remind"
      } 
    },
    "action-cancel": {
      "href": "/invitations/15623/status",
      "docs": {
        "href": "/docs/invitations/action-cancel"
      }
    }
  }
}
----

.The same invitation after it has been accepted.
[source,jsonc]
----
// GET /invitation/15623
{
  "status": "ACCEPTED",
  "_links": {
  }
}
----

This provides everything the LLM-agent-driven client or a human needs.
Description of resources, documentation, allowed operations. Meanwhile MCP exposes all possible operations.
The documentation may be inaccessible to an agent, or may belong to an older version.

.Available operations for the agent upon discovery.
[source,text]
----
invitation_create(...)
invitation_send_reminder(...)
invitation_cancel(...)
invitation_get(...)
----

== So why not have some REST?

Because people still don't know or bother to think in REST terms. Devs work, invent their own 
conventions until someone rewrites them in their own subset of RESTful traits and more ad-hoc
conventions plus legacy support.
